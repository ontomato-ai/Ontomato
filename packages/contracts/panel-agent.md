# Panel operation intents and human confirmation

Status: proposal and contracts only. Channel/host changes require review by their owner before implementation. No runtime, UI, SDK or skill-core implementation is included in this commit.

## Current boundary

Node owns the operation intent, its confirmation association and one dispatch claim. The channel owns generic questions, recipients, persisted answers and truthful provenance. Java owns application admission, product Grants and business execution permissions. The SDK and its client owner own the operation implementation.

The first server operations are `platform:ScheduledTask.save` and `schedules.runNow`. The browser keeps its current human path and credentials; it does not forward an agent's business call or receive executor credentials. A state/navigation operation requires a real addressed instance and acknowledgement; no new instance-dispatch protocol is added for operations the trial does not use.

## Skill-system boundary

Panel skill provision is deferred to the generic capability-source extension owned by the separate skill-system line. Until that interface is ready, Java emits no panel-use page-skill mappings; the separately committed removal of ApplicationPanelUse.skill preserves use locators/defaultAgentId and legacy mappings. This proposal neither publishes a universal panel identity nor adds a panel catalogue, describe/loading endpoint, per-user package or skill-loading branch: a panel will only supply a standard domain Agent Skills package through the agreed generic source interface, and the capability/A-package owners keep catalogue, selection, admission, menu intersection and runtime loading.

The source gap and rejected file-copy/publication workarounds are handed over separately. Dynamic business data/forms remain the existing owners' interfaces; this document is only operation coordination and human confirmation, not a new skill system design.

## Findings behind the human route

- `agent-runtime/src/channel.ts` already delivers ordinary child `needsInput` to its parent; its no-parent branch already records a question for that conversation's user. Preserve both ordinary clarification behaviors.
- `channel-store.ts:pendingQuestions()` currently selects a question only when its source session equals its receiving session. Simply sending a child's question to the root will not make it a pending human question.
- Existing web replies carry `replyTo`; the runtime constructs their true `source:{kind:'user'}`. Agent sends have the actual execution source. `ShellQuestions` currently sends text, losing the chosen option index.
- `channel.actor.id` is a Java caller reference, not a user ID. Use existing caller restoration for the actual initiator. Do not compare caller UUIDs to user IDs or require caller references to remain identical across human turns.
- `credentialsForRun(owner,runId,initiatorCredentials,sessionId)` rejects a closed or mismatched run and resolves its fixed executor with current credentials. Returned credentials already carry the run caller-scope headers.

## Proposed generic route, for the channel owner

The shapes in `src/agent-user-questions.ts` are proposed private channel transport, not a new business option of the agent tool.

1. Node restores the requesting execution, initiator and actual root from trusted run/admission facts. It reserves a separate server-assigned questionId with the immutable intent (one-to-one per domain), then generates the question from that intent: operation, target, input and execution user. Zero-based option 0 means do not execute and is the default; option 1 means execute this one call. No model-authored confirmation text grants permission.
2. Add a generic nullable `userRecipient` delivery context to trusted run admission/prepare facts: the authenticated human host sets its own receiving session and caller reference, ordinary child admission inherits it, and a source without a verified human recipient keeps null. It is not a model command/context parameter, an executor identity or an intent reference. Node and Java human hosts must both supply it; runtime propagation preserves it rather than inferring human presence from actor.id or an arbitrary root trace. Proposed service-only `POST /v1/channel/user-questions` takes `AgentUserQuestionRequest`. Node allocates a separate questionId and persists its one-to-one association with the intent before delivery; a caller cannot pick or reuse that questionId through an intent ID. Reuse the existing input/admission Idempotency-Key with this server-assigned questionId, so an explicit retry delivers the same question; no new idempotency protocol is added. The channel replay check includes the explicit-user route marker, real source and immutable question payload, so an ordinary clarification cannot be adopted as this question. The body has no arbitrary recipient. For this route the human host declares its own root session, and children inherit it; the channel resolves that trusted userRecipient and checks its receiving scope. Other-root guessing is not supported. An external/background root or missing human session returns `USER_SESSION_UNAVAILABLE`, with no parent-agent substitute.
3. Persist an ordinary `agent-question` in that human session, marked with the proposed generic notification field `recipient:'user'`. Keep its actual child execution as `source`. It is an output/notification, not a pending model input that would make the root answer its own question. Return `AgentUserQuestionReceipt` and emit the existing question/session updates.
4. Extend `pendingQuestions()` to include explicitly user-addressed questions. Such a question is answered only by the real human receipt in its receiving session. Agent/external answers must neither approve nor remove it from the user's list. The source execution's `questions()` view uses the same receiving question/answer facts.
5. Put this authoritative pending-question list into the existing long-lived session/tasks snapshot. The root's last run may already have finished, so live display must not depend only on that run's stream or client-loaded history. Initial/history and session updates reuse the same owner query. No new question table, UI component or polling is added.
6. Add optional `selectedOption` and the host-derived respondent caller reference to the existing authenticated human send/reply path and persisted answer; never reconstruct a past respondent from the latest session binding. The host supplies the respondent caller from verified identity. Validate the index against the stored options; absent selection is free text, not approval. Include selection in existing input-ID replay/conflict checks, so a request cannot reuse one input ID with another choice.
7. After persistence and outside the session admission lock, notify the question's source provider over existing service-authenticated provider transport. Proposed action `user-question-answer` carries only `AgentUserQuestionAnswered`, not an intent or business decision. A reply relayed to its source execution retains genuine user provenance and the root receipt reference, never a parent agent's endorsement.
8. Proposed private `GET /v1/channel/user-questions/:questionId/answers/:answerId` returns `AgentQuestionAnswerReceipt` from persisted input, scoped to the participating host/tree and domain. Node reads it rather than trusting callback content or a skill's claimed answer. Notification failure is exposed without a new retry/outbox. A later explicit intent dispatch reads the same evidence; it is not another authorization route.

Question/answer provenance remains the original user/agent/external fact; consuming an operation authorization does not write or overwrite business confirmedDecisions. The provider notification uses the source run's original initiator transport, never executor credentials. A human reply may use another caller reference; Node restores both through the existing caller owner and compares the actual initiator user/domain. It does not put executor identity/keys into generic question metadata or borrow the reply's browser credential for an old run.

## Node intent and one dispatch

`PanelOperationIntent` is one minimum invocation fact in the existing Node product service: source session/run, root session, use reference, resolved panel/projection/binding/operation, immutable call, actual initiator, fixed executionUserId, questionId/answer provenance, dispatched and owner outcome. Answer text remains in the channel; Node does not duplicate it. It has no credential, signature, frozen revision or workflow transitions.

- Resolve the current Java use and panel/projections through their existing admission/use owners. Resolve operationId from the current manifest slots/projections and the same-version SDK catalogue/port derivation shared with the SDK; never parse labels/HTML or execute module text. Validate the supplied target type against that declaration, leaving business access to its owner. Do not create a second skill/menu permission calculator or a Node class-permission list.
- Do not accept handlerRef, executor, root setting, questionId or an answer receipt from a skill. A new invocation gets a new intentId and Node-owned question association (unique per domain); toolCallId is trace data, never authorization. Reusing an intent ID with different target, input or source is a conflict requiring a new intent.
- Node owns one confirmation boolean per `(domain,root provider,root session)` and its restored owner. No row means confirmation on. Initialize from trusted admission/root ownership, not model-selected roots. Only the authenticated owning user's UI path may update it, using the existing owning-provider exact session-owner check, not administrator/maintainer or merely readable-session access. Children use that same root setting.
- Settings affect new intents. Turning automatic mode on neither executes an old pending question nor saves a draft. A new session defaults to confirmation on.
- Default form.save produces the existing unsaved PageDraft only. Its form holds the owner's field values, with the relation's pageKey and derived save operation. The standard skill script writes the existing draft artifact and link; no business write or redeemable chat save confirmation is created.
- Default runNow creates the human question above. Only option 1 on its linked persisted question, from the authenticated initiating human in the actual recipient session, approves. Free text, defaults, skip/timeout, parent answers and possession of questionId do not approve.
- Before dispatch, call credentialsForRun for the stored source using its original initiating context. Compare its fixed executionUserId and the newly resolved operation/binding to the recorded call. Changed target/input, executor or operation requires a new intent. Do not load an old product version or invent a hash/freeze mechanism.
- The standard skill command handles confirmation-required by keeping the same code-tool invocation waiting on the dispatch endpoint, not returning a final model answer that closes its source run. Dispatch waits for the generic persisted-answer notification or original run cancellation/closure, using a request-lifetime waiter and existing run events, holding no database/session lock and adding no polling, deadline or second task state. The provider's answer notification must happen independently of safe-boundary model input consumption, so it can complete this waiting tool; otherwise waiting for the tool boundary would deadlock. Waiters retain no executor key: restore it only when an actual dispatch is eligible. The database intent and channel receipt remain authoritative; a lost HTTP connection never releases a dispatch claim, and an explicit later call reads those same facts.
- Atomically claim dispatched=false to true before the owner call. Never reset it on refusal or unknown outcome. Repeated tool/dispatch calls return the recorded fact without invoking again. If the source run has closed, return RUN_CLOSED; do not wake another run or redeem it under a parent's executor.
- Automatic mode makes an explicit save/run call through the same owner path, without a question. It does not bypass authorization. runNow uses the task service's existing Idempotency-Key with intentId. An unknown result is reported/inspected, not released for replay.

### Node API shapes

These are operation APIs, not skill publication, catalogue or loading APIs. Their caller context comes from the existing fixed execution callback, retaining its GET/POST/run/path restrictions. The source session is restored from the owned run, never selected in the body, and must match the stored invocation for dispatch. Reading an existing intent is an initiator-owned data read, independent of source-run liveness or executor key validity.

| Method/path | Body | Result |
| --- | --- | --- |
| `POST /api/assistant/executions/:runId/panels/operate` | CreatePanelOperationIntentRequest | PanelOperateResponse |
| `GET /api/panel-operation-intents/:intentId` | No body; authenticated initiator owner | PanelOperationIntent; no executor recovery |
| `POST .../panels/intents/:intentId/dispatch` | Empty object | PanelOperateResponse; only the stored call can dispatch |
| `GET /api/panel-operation-settings/:providerId/:sessionId` | Authenticated owning human, no body | PanelOperationSettings |
| `PUT` same settings path | UpdatePanelOperationSettingsRequest | PanelOperationSettings |

Use direct fixed coordinator handlers under the existing `/api/assistant/executions/:runId/` sealed callback prefix, not the general workbench/ontology business proxy: that proxy switches to executor credentials, whereas product admission must keep initiator. `unwrapCallbackCredential` restores the initiator and checks run/path/expiry; coordinator routes require that callback context, and use credentialsForRun only for the nested owner call. The Node host issues the existing sealed callback capability and a coordinator URL in the run environment in both self and specified-user modes; this changes no skill loading and exposes no executor key. The ordinary intent GET is also available to scripts through the existing workbench ownership-read proxy, classified as initiator data before executor resolution; it never dispatches or calls credentialsForRun. Settings routes are excluded from skill callback credentials. The generic provider answer notification is service-only, not a public approval endpoint. A source that has ended cannot be revived through these APIs.

## Shared operation implementation and execution identity

The SDK's current ScheduledTask code already gets a task and its owner form, sends update at the caller-supplied revision and runs now through createSchedulesApi. Move that request orchestration to a pure client module in the existing platform-schedules package, then call it from both SDK and Node with explicit request ports. Browser registry/import changes go to P4's file owner. Node uses only the fixed save/run operations with credentialsForRun's executor/caller headers; there is no model-supplied URL or browser forwarding.

Keep the revision read when a form/draft was obtained. Fetching unchanged task fields or the owner's formRevision before update must not replace that supplied task revision with the latest value. Preserve the owner's refusal and structured form errors and the complete C-package caller headers. Carry the run's actual authority/build-test context; absent client headers cannot turn a test run into live execution, and an unsupported management-write test context is refused. Any added workspace dependency updates public and enterprise lockfiles together.

The old PLATFORM_DRAFT_RULE must not forbid the declared operation entry. Scope it to direct writes from unconverted hand-written page skills, and explain read / unsaved form draft / declared coordinated operation for panel operations. Existing manual scripts keep their guards. Do not identify a universal panel skill or change package loading to do this; the coordinator's actual declared-operation boundary is what permits a call.
