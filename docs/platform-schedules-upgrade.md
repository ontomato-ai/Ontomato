# Upgrade to platform schedules

Use this procedure when upgrading a deployment with workbench agent-runtime schedules or DataRAG write tasks. A fresh installation creates its own empty platform tables. The migration command is included in the new DataRAG image.

1. Record the old Node schedule zone (`SCHEDULE_TIMEZONE` or the old process zone), the old JVM zone, the Java `SERVICE_ID`, each database connection and the workbench `PG_SCHEMA`. Preserve the existing runtime tokens for this upgrade. The import uses the old workbench token to open existing credentials and the ontology token to seal them for DataRAG. For custom connections, pass `SCHEDULE_SOURCE_JDBC_URL` and `SCHEDULE_SOURCE_USER/PASSWORD` to the migration container. The destination honors `DATA_ENGINE_JDBC_URL` and `SCHEDULE_TARGET_USER/PASSWORD`. Credentials otherwise come from the deployment's `POSTGRES_USER/PASSWORD`.
2. Arrange a maintenance window, suspend automatic updates, quiesce writes, and let in-flight functions finish. Stop both old application processes, keeping PostgreSQL available. Take restorable backups of the workbench and DataRAG databases, the runtime data and the deployment configuration. Record counts for `scheduled_tasks`, `scheduled_task_runs`, `write_task`, and `write_task_result` where present.
3. Select the new DataRAG image in Compose. Run the import without starting an application. In the command below replace `enterprise` with `oss` for the public edition and supply the two zones recorded in step 1, in Node/JVM order. The default source databases are `data_agent` and `ontomato`, respectively. The default destination database is `datarag`. Use the deployment's Compose files and environment for both commands.

   ```sh
   docker compose run --rm --no-deps --entrypoint java datarag \
     -cp '/app/lib/*:/opt/datarag/lib/*' io.ontomato.dataengine.schedules.ScheduleMigration \
     import enterprise Asia/Shanghai Asia/Shanghai
   ```

   The import preserves task and run IDs. Agent tasks retain their owner, prompt, agent, cadence, next slot, notifications and session links. The sole OSS workbench user `system/1` maps to the sole DataRAG user `admin/1`. Function tasks retain domain ownership, the function reference, Cron expression, enabled state, timestamps and results. Their old history has no trigger field and is shown as `unknown`. No function task needs an owner mapping. An unreadable agent credential pauses enabled tasks until the owner opens the page with a valid login.

   The destination import is transactional and a completed import is repeatable. An invalid rule or target, a foreign service ID, an ID collision, or an orphan result requires investigation. Keep both sources and the backups. Correct the affected source row, or archive the rule, referenced function and results and obtain the site's decision to exclude it before retrying. Historical pre-runtime `analysis_schedule_rules` deployments require a separate baseline upgrade.
4. Compare imported task and execution counts against the source counts broken down by kind (`owner_id IS NULL` for function tasks), as well as representative Cron, interval, paused and disabled rules. Inspect `platform_task_credential.valid` for agent owners needing a login. Run the **same** command with `retire` in place of `import` to drop the old source tables. Keep both old services stopped until retirement finishes. Retirement can resume after a partial cross-database drop.
5. Start the new combined deployment, using its workbench service as DataRAG's `WORKBENCH_INTERNAL_URL`. Verify an automatic agent conversation and a real function write from the platform page. Check application and agent filters, owner isolation, and function visibility for a domain member with and without the existing write-task grants. Verify completion mail with the site's SMTP configuration if used. For a rollback, stop the new version, restore the matching backups and run the old images together. Any writes made after the cutover must be reconciled before restoration.
